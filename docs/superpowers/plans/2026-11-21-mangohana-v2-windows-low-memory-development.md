# MangoHana V2 Windows 저메모리 개발 안내

2026년 11월 21일 · 현재 Windows 16GB 노트북 기준

**Windows 가용 RAM 때문에 Linux 0B가 대기 중이어도 제품 개발은 진행할 수 있다.** 저장해 둔 OCR 응답과 시험용 번역·복원 응답을 기존 제품 검사 코드에 넣으면 글줄과 좌표 연결, 번역 요청·응답 검증, 접수·저장·복구까지 확인할 수 있다. 개발할 때는 바꾼 기능에 해당하는 검사 파일을 한 번에 하나씩 실행한다.

여기서는 현재 품질 계획 7개와 서비스 개선 계획 8개에 대해 Windows에서 시작할 코드, 사용할 입력, 확인할 결과를 정리한다. 제품 계약과 적용 순서는 기존 계획을 따른다. [품질 개발 계획](2026-11-20-mangohana-v2-text-coverage-and-translation-quality.md) · [서비스 개선 계획](2026-11-20-mangohana-v2-service-improvements.md) · [기준 문서 목록](../../source-reference.json)

## Windows에서 개발할 품질 과제

## 모델 호출 없이 손볼 복원·식자·실행 기록

- **원문 제거와 그림 보호**는 작은 마스크와 미리 만든 복원 이미지를 넣어 시험한다. 같은 글줄 ID에 마스크와 결과가 붙는지, 허용 범위 밖의 픽셀·알파가 바뀌지 않는지, 잘못된 크기나 손상 PNG를 게시하지 않는지 확인한다. [마스크 계약 검사](../../../tests/v2/stage10-mask-contract.test.mjs) · [제품 결과 검사](../../../tests/v2/linux-0b.test.mjs)
- **한국어 식자**는 합성 대사와 고정 말풍선으로 배치 대상, 글꼴 크기, 줄바꿈, 좁은 공간의 수동 배치 안내를 개발한다. 폰트와 실제 렌더러의 픽셀 검사는 메모리 여유가 있는 때 기존 작은 합성 Canvas 경로로 확인한다. [기존 식자 증거](../../validation/2026-11-19-v2-web-product-engine-integration.md#5-결정적-검증과-한계)
- **0B 실행 기록과 실패 분류**는 모의 모델 응답과 보관한 자원 로그로 시험할 수 있다. 메모리 부족, 호환성 오류, 시간 초과, 비정상 출력, 이미 호출한 단계, 정리 미확인을 구별하고 다음 호출이 막히는지 검사한다. [모의 실행과 기록 재검토](../../../tests/v2/linux-0b.test.mjs)

## 창을 더 띄우지 않고 쓰는 작업 순서

1. **코드와 입력부터 고른다.** 이번 변경에 해당하는 함수나 경로 하나와 실패 사례 한 가지를 고른다. 기존 저장 응답은 읽기용으로 사용하고, 고칠 원고·응답은 시험용 사본을 만든다. 실제 모델을 띄우는 대신 해당 단계를 가짜 응답으로 연결한다.
2. **작은 회귀부터 실행한다.** 예를 들어 줄 ID가 빠지는 문제라면 OCR 매핑 또는 번역 규칙 검사부터 실행한다. 새 실패를 먼저 재현하고 같은 검사로 수정 결과를 확인한다. 무거운 프로그램을 함께 띄울 이유가 없는 동안에는 Windows Node 또는 Python만 실행한다.
3. **변경이 경계를 넘을 때 검사 범위를 넓힌다.** 제품 API·CLI 연결에는 작은 원고와 loopback HTTP, 저장소에는 기존 테스트 저장소를 쓴다. 브라우저, 격리 DB, 전체 빌드, 대형 파일은 변경이 해당 기능에 이를 때 순서대로 점검한다.
4. **경곗값과 실제 알 수 있는 값을 기록한다.** 원본과 사용자 변경값, 기존 결과, 계정 소유권, 수정 버전과 승인 수를 보존한다. 미확인 응답이나 비용을 실패·0원·자동 재시도로 바꾸지 않는다. 기존 Electron 저장소의 미커밋 변경, `.ctp`, IPC는 보존한다. [공통 작업 기준](../../reference/trio-main/AGENTS.md) · [검증 하네스](../../agent-harness.md)

Windows에서 실행하는 테스트에는 원칙적으로 합성 계정·파일·자격 증명을 쓴다. 저장된 관측 자료는 기존 검증에 승인된 범위에서 읽고, 제품에 특정 파일명·정답 문구·고정 좌표를 심어 시험을 통과시키는 방식은 사용하지 않는다.

## 바로 실행할 수 있는 PowerShell 명령

저장소에서 요구하는 Node 범위는 `>=24.11.1 <25`다. 이 PC에서는 설치된 Codex 관리 실행기 `v24.22.3`을 지정했다. 기본 `node`가 다른 버전일 수 있으므로 아래 명령은 선택한 실행기의 버전을 먼저 확인한다. 설치된 다른 Node 24 경로를 쓸 때도 같은 범위를 확인한다. [저장소 런타임 조건](../../../package.json)

```powershell
Set-Location -LiteralPath 'C:/dev/Projects/mangohana'
$Node24 = Get-Command node -All |
  Where-Object { $_.Source -like '*CodexPrimaryRuntime*' } |
  Select-Object -First 1 -ExpandProperty Source
if (-not $Node24) { throw '설치된 Node 24 실행 파일의 전체 경로를 지정하세요.' }
$NodeVersion = & $Node24 --version
if ($LASTEXITCODE -ne 0 -or $NodeVersion -notmatch '^v24[.][0-9]+[.][0-9]+$' -or
    [version]($NodeVersion.TrimStart('v')) -lt [version]'24.11.1') {
  throw '이 저장소가 지원하는 Node 24 실행 파일을 사용하세요.'
}
$NodeVersion
```

**OCR 연결과 번역 규칙 51건.** 이 두 검사 파일은 프로세스 하나에서 실행되는 것을 확인했다. 다른 검사는 시험 파일 간 격리를 유지하고 동시 파일 수를 1로 둔다. [Node 검사 옵션](https://nodejs.org/api/cli.html#--test-isolationmode)

```powershell
& $Node24 --test --test-isolation=none --test-reporter=spec tests/v2/stage09-ocr-mapping.test.mjs tests/v2/stage11-translation-contract.test.mjs
```

**평가 자료·집계·품질 정책 132건.** 누락 측정 업무를 시작할 때 기준 검사로 쓴다.

```powershell
& $Node24 --test --test-concurrency=1 --test-reporter=spec tests/v2/evaluation-dataset.test.mjs tests/v2/offline-evaluation.test.mjs tests/v2/quality-policy.test.mjs
```

**작은 글자·빈 말풍선 2건.** 같은 관리 실행기에 들어 있는 Python 3.12와 기존 Pillow를 사용한다. 설치되어 있는지 확인한 경로에서 실행한다.

```powershell
$RuntimeDependencies = Split-Path -Parent (Split-Path -Parent (Split-Path -Parent $Node24))
$Python312 = Join-Path $RuntimeDependencies 'python/python.exe'
& $Python312 --version
& $Python312 -B -m unittest discover -s tests/v2 -p 'test_local_review_coverage.py' -v
```

다른 Node 검사는 표의 `.test.mjs` 파일 하나를 골라 `& $Node24 --test --test-concurrency=1 <파일>`로 실행한다. TypeScript 도메인 시험은 이미 설치된 Vitest를 쓰는 `& $Node24 node_modules/vitest/vitest.mjs run --maxWorkers=1 <파일>` 경로가 있다. 다음 묶음은 선행 조건을 확인해 필요할 때 선택한다.

## 실제 모델과 제품 판정에 필요한 검증

- **Linux 0B 한 장**은 기존 CPU 4개 분량·컨테이너 RAM 6 GiB·스왑 0·PID 256을 적용한다. 착수 시 Windows 7,168 MiB와 WSL 6,912 MiB, OCR·Qwen·LaMa 각 최대 1회 승인 범위를 확인한다. 적재·계산·출력·전체 페이지·종료를 각각 기록한다. 실제 4 GiB 경로는 해당 모델의 적재와 계산, 그리고 별도 실행 범위 확인이 남아 있다. [저메모리 계획](2026-11-20-mangohana-v2-linux-0b-low-memory.md) · [0B 검증 안내](../../validation/2026-11-20-v2-headless-linux-0b.md)
- **계속 RAM 확보가 어려운 경우** 가용 메모리가 충분한 WSL2 환경에서 같은 고정 입력과 모델 지문으로 시험할 수 있다. 일반 Linux 서버를 선택하면 현재 실행기의 WSL2 전용 시작 조건과 Windows 메모리 감시를 해당 Linux 운영 환경에 맞춰 검증한다. 외부 장비로 자료를 옮기거나 실제 모델을 돌리는 범위는 기존 승인 절차를 따른다. [실행기](../../../scripts/v2/linux-0b/launch.py)
- **실제 웹·품질 인수**는 운영 담당 프로그램 연결과 실모델이 있는 환경에서 업로드부터 저장·다시 열기·다운로드까지 확인한다. 새 원고에서 문자 누락, 번역 의미와 자연스러움, 원문 잔상, 작화 보존, 식자 가독성을 사람 검수와 함께 판정한다. 현재 확인한 공통 웹·CLI 엔진의 범위는 `INTEGRATED_OFFLINE_ONLY`다. [제품 통합 기록](../../validation/2026-11-19-v2-web-product-engine-integration.md) · [최종 인수 조건](../../validation/2026-11-19-v2-stage16-final-acceptance.md)

## 작업을 마칠 때 남길 기록

각 변경에서 작업 유형(원인 분석·샘플 보정·제품 개선·제품 검증), 바뀐 파일, 사용한 시험 자료, 정확한 명령과 성공·실패 건수, 확인한 제품 경로, 미검증 항목을 남긴다. 가짜 응답이나 저장 응답을 통과시킨 결과, 새 이미지를 자동으로 처리한 결과, 사람이 페이지를 합격시킨 결과는 각각 해당 근거로 기록한다. 실제 AI 비용·권한·파일을 쓰는 검증과 배포, 커밋·푸시는 승인 범위를 확인하고 진행한다.

## 보관 원고에서 남은 자동 식자 여백

- [x] 원문과 이웃 대사 간격을 지키는 흰색 내부, 그리고 원본·마스크·복원으로 다시 확인한 회색 내부에서 조금 더 큰 글꼴을 실측한다. 줄 수나 어절 갈라짐이 늘거나 실제 픽셀 검사를 통과하지 못하면 기존 후보를 사용한다.

## 좁고 긴 말풍선에서 읽기 어려운 대사

직전 보관 원고의 4번은 17px 세 줄, 13번은 26px 한 줄이다. 같은 한글을 크게 넣을 수 있는지 실제 글꼴과 완성 PNG로 확인한다. 공유 말풍선은 이웃 대사의 위치와 읽기 순서를 지키고, 단독 말풍선은 닫힌 내부의 가운데 폭과 글자가 차지하는 높이를 함께 본다.

- [x] 같은 줄 수로도 글자를 키울 수 있는 공유 말풍선과, 가운데가 넓은 단독 말풍선을 합성 픽셀로 재현한다. 사용자 지정 크기·허용 범위·보호 그림을 포함한 대조군을 확인한다.
