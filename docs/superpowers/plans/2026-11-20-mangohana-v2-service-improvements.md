# MangoHana V2 서비스 점검에서 나온 여덟 가지 문제를 고치는 순서

2026년 11월 20일 · 개인 PC에서 개발하고 여러 사람이 쓸 웹서비스까지 확인하는 실행 계획

**첫 수정은 ‘재개’ 버튼입니다.** 서버가 바빠서 원고를 받기 전에 거절했다면, 자리가 났을 때 같은 접수 번호로 다시 보낼 수 있어야 합니다. 서버가 이미 원고를 받고 답만 잃어버렸다면, 같은 번호로 진행 상황을 찾아야 합니다. 이 두 상황을 구별해야 기다림을 줄이면서 중복 번역도 막을 수 있습니다.

아래 번호는 [서비스 시작 전 점검 보고서](../../mangohana-v2-service-readiness-and-performance.md)의 번호입니다. 권장 수정 순서는 **1 접수·재개 → 6 계정별 처리 → 7 중단 복구 → 3 진행 조회 → 4 파일 전송 → 5 저장·다운로드 → 2 모델 준비 → 8 실제 원고 품질 판정**입니다. 여러 사람이 같은 일을 두 번 실행하거나 남의 결과를 받는 문제부터 막고, 그 위에서 속도를 개선합니다. 2번의 시간 측정과 8번의 평가 기준 준비는 앞에서 시작합니다.

## 지금 내 Windows PC에서 할 일

지금 확보할 수 있는 것은 **현재 문제가 보이는 장면과 고친 뒤 비교할 숫자**입니다. 다음 시험은 예시 계정, 임시 작업실, 시험용 그림과 정해진 답을 돌려주는 가짜 번역기로 준비할 수 있습니다. 원래 작업실, 71장 결과와 14~16단계 검증 자료는 비교용으로 보관합니다.

## 개인 PC에서 Linux 0A를 통과하는 시점

0A는 **서버에 쓸 프로그램을 내 PC의 Linux 안에서 안전하게 켜고 끌 수 있는지** 확인하는 첫 환경 시험입니다. 최근 기록상 Windows 비교 자료가 있고 Linux의 여덟 환경 항목은 모두 확인 대기입니다. 이 여덟 항목은 위의 여덟 개선 과제와는 별개의 시험 목록입니다. [Windows 비교 자료](../../validation/2026-11-20-v2-headless-preflight.md) · [Linux 항목별 판정표](../../validation/2026-11-20-v2-headless-linux-resumption.md)

1. **환경부터 준비합니다.** 승인된 WSL2와 Ubuntu 24.04를 개인 PC에 준비할 때는 시스템 변경·재부팅 전에 열린 작업의 저장 상태와 영향을 확인합니다. Ubuntu의 정상 기동을 확인한 뒤 Docker Engine이 필요한 범위와 추가 설치 승인을 별도로 다룹니다.
2. **가짜 입력으로 Linux를 검사합니다.** 관리자 권한 없이 프로그램을 담는 공간(컨테이너)을 사용하고 Chromium 브라우저의 보호 기능을 켭니다. 작업 1개·2개의 CPU·메모리가 지정한 한도 안에 드는지 재고 정상 종료·취소·시간 초과·강제 종료 뒤 남은 작업 프로그램이 0개인지 봅니다. 같은 글꼴과 320×240 및 2039×2880 시험 그림으로 긴 한국어, 여러 말풍선, 복잡한 배경을 Windows와 비교합니다. 글자가 들어가는 칸은 누락·잘림과 보호 영역의 그림 변경이 0건이어야 하고, 너무 좁은 칸은 사람이 배치해야 한다고 표시해야 합니다. AI 실행 도구(ONNX)를 불러오는지, 배경 복원 도구(LaMa)가 모의 응답과 취소를 처리하는지, 두 웹 실행 방식(Next·Vinext)에서 화면과 요청 통로가 작동하는지도 확인합니다.
3. **결과에 따라 나아갑니다.** 필요한 항목이 모두 통과하면 제품 수정과 다음 시험을 검토합니다. 실패나 증거 누락이 있으면 그 항목과 원인을 남기고 위의 Windows 준비를 계속합니다. **0B**는 별도 승인을 받아 실제 모델이 한 장을 처리하는지 보는 시험입니다. **0C**에서는 기존 저장·복구 기능을 임시 자료로 시험해 편집값 보존, 담당자 교체, 그림 파일 복구를 확인합니다. 이 근거를 큰 서버 변경 전에 갖추고, 연결한 뒤에는 6·7번에서 사용자 화면부터 다시 시험합니다. 1번 접수 수정의 판정은 가짜 번역기로 가능합니다.

## 0A 뒤에 고칠 일과 통과 기준

아래 확인칸은 앞으로 실행할 작업입니다. 제품 수정은 0A의 증거가 확보되고 구현에 착수할 때 시작합니다.

### 첫 수정 · 문제 1. 접수와 재개

현재 서버는 다른 묶음을 저장 중일 때 원고 접수에 들어가기 **전에** ‘업로드 중이라 거절’이라는 코드(`BATCH_UPLOAD_BUSY`, HTTP 429)를 줍니다. 화면은 이를 다른 통신 오류와 함께 ‘접수 여부 모름’으로 처리합니다. 첫 수정에서는 화면의 보내기 함수(`processProjectBatch`)가 이 응답을 구별하고 저장하게 합니다. 서버의 기존 접수·조회 함수(`submitBatch`, `resolveBatch`)를 써서 같은 계정·작품·접수 번호·원본이면 먼저 등록한 작업에 연결합니다. [서버의 거절 지점](../../../apps/engine/server.mjs) · [화면의 보내기·재개](../../../apps/sites/lib/studio-batch-engine.ts) · [작업 번호 중복 방지](../../../apps/engine/store.mjs)

- [ ] **먼저 실패 장면을 고정합니다.** A가 30장을 ‘작품 전체 보내기’로 올리는 동안 접수를 잠시 붙잡아 둡니다. B는 별도 작업실에서 1장을 같은 방식으로 보냅니다. 현재 버전에서 B의 ‘재개’가 조회만 반복하는지 확인합니다.
- [ ] **화면이 증거에 따라 두 가지로 동작하게 합니다.** 이번 전송에서 서버의 정확한 혼잡 거절을 받으면 원래 접수 번호·원본 목록을 그대로 두고 ‘다시 보낼 수 있음’을 먼저 저장합니다. 그 뒤 B가 재개를 누르면 같은 번호로 보냅니다. 시간 초과, 깨진 응답, 이유가 다른 429, 단순 ‘기록 없음’은 기존 번호로 조회합니다. 저장에 실패하거나 다른 탭에서 더 최신 결과를 저장했으면 추가 전송을 멈춥니다. 예전 버전에서 ‘보내는 중’으로만 남은 작업은 거절 증거가 없어도 보존하고, 서버에서 접수·미실행 중 무엇이 확인되는지에 따라 복구합니다.

| B에게 일어난 일 | 고친 뒤 사용자가 보게 될 결과 | 통과를 확인하는 수치 |
| --- | --- | --- |
| A 때문에 접수 전 거절. A의 접수가 끝난 뒤 B가 재개 | B의 원고가 원래 번호로 접수되고 결과 한 장이 열립니다. | 최초 거절과 재전송을 합쳐 전송 시도 2회, **B의 실제 접수 1건·가짜 번역 1회** |
| 서버가 접수한 직후 답만 유실. B가 창을 닫았다 열고 재개 | 저장된 번호로 기존 작업과 결과를 찾습니다. | 접수 뒤 **원본 재전송 0회**, B의 작업·가짜 번역은 각각 1건 |
| 접수 여부를 끝내 확인하지 못함 | ‘접수 확인 중’과 원래 번호가 남습니다. | 새 번역 호출·중복 비용 반영 0건. 이전 호출의 비용은 확인될 때까지 ‘미확인’으로 기록 |
| 두 탭이 같은 번호로 재개하거나 원본이 바뀜 | 같은 원본이면 기존 작업 하나에 연결합니다. 바뀐 원본은 기존 결과를 덮어쓰지 않고 충돌을 보여 줍니다. | 같은 입력의 중복 작업 0건, 다른 입력이나 다른 계정의 결과를 잘못 연결한 경우 0건 |

기존 접수 조회와 예전 저장본 시험도 함께 통과해야 합니다. 실패하면 새 재전송 분기만 끄고 보관한 번호로 조회합니다. 첫 수정에는 모델 교체, 저장 형식 전체 변경, 대기열 교체를 묶지 않습니다. [기존 작업실 시험](../../../apps/sites/checks/batch-engine.test.mjs) · [실제 HTTP 접수 시험](../../../tests/v2/batch-http.test.mjs) · [재시작·중복 방지 시험](../../../tests/v2/batch-recovery.test.mjs)

### 다음 두 작업 · 문제 6과 7. 여러 사람의 작업을 맡고, 멈춰도 되살리기

#### 문제 6 · 계정별 처리

1번의 접수 규칙을 공통으로 쓰고, 0C에서 확인한 작업 기록장(PostgreSQL)과 비공개 그림 보관함을 연결합니다. 웹 서버가 로그인한 사람을 확인해 번호를 발급합니다. 번역 담당 프로그램이 글자 읽기 → 번역 → 배경 복원 → 한국어 배치를 맡습니다. PC와 서버는 같은 처리 코드를 쓰고, Windows 앱의 창을 여는 Electron은 개인용에만 둡니다. 서버용 시작 함수는 현재 ‘처리 기능 미연결’에서 멈춥니다. 네 단계가 실제로 연결되고 필요한 자원이 준비된 경우에만 새 일을 받게 합니다. [서버 진입점](../../../apps/api/src/server.ts) · [담당 프로그램 시작](../../../packages/operations/src/runtime-startup.ts) · [기존 처리 단계 연결](../../../packages/operations/src/pipeline-runtime.ts)

- [ ] **고치고 확인합니다.** 하나의 작업 기록장을 사용하고 처음에는 한 쪽씩 처리합니다. 예시 계정 A·B가 모두 기다리면 한 계정이 줄 전체를 독점하지 않게 차례를 줍니다. A의 첫 쪽이 처리 중일 때 B의 한 장이 이미 접수된 두 계정 시험에서, B가 A의 나머지 29장을 모두 기다리지 않고 차례를 받아야 합니다. A는 B의 번호를 알아도 진행 상황·원본·결과를 하나도 열 수 없어야 합니다. Linux의 실제 연결은 승인된 모델과 글꼴로 브라우저 접수부터 결과 재열기까지 확인합니다. 가짜 입력만 성공하면 ‘계정과 대기 순서 확인’까지만 기록합니다.
- [ ] **실패하면** 서버의 신규 접수를 닫고 접수한 번호는 계속 조회할 수 있게 합니다. 이미 접수한 원고를 개인용 엔진에 다시 보내지 않습니다. 기존 개인용 작업실은 자기 작업을 계속 엽니다. [담당자와 작업 유효 시간](../../../packages/domain/src/execution.ts) · [서버 연결 시험](../../../tests/postgres/pipeline-runtime.test.ts)
