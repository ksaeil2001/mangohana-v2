# Trio 상태 흐름 감사

대상: 이 저장소에서 배포되는 Trio 작업실. 최초 기준 버전: `4b2e211` (Sites v1), 가장 최근 후속 감사 기준: `5fa3179` (Sites v14). Windows의 OCR/번역 엔진과 별도 Trio 사이트는 대상이 아니다. `app/page.tsx → components/studio.tsx → lib/studio-*`의 도달 가능한 코드와 Worker 진입점을 확인한다. 사용하지 않는 스타터 UI 및 외부 라이브러리 내부 상태는 감사 수에 넣지 않는다. 아래 목록은 현재 코드 기준이며 이후 절은 변경 이력을 기록한다.

## 확인한 결함과 검증

구체적인 결함, 변경된 전이와 검증 결과는 구현 후 이 문서 아래에 기록한다. 전부 거대한 상태 관리 라이브러리로 바꾸지 않고, 충돌하거나 데이터 보존을 위협하는 경계만 명시적으로 만든다. 나머지 단순 enum·토글은 그대로 둔다.

## 반영한 전이 규칙

- **UX:** 입력 중인 번역문도 저장 대상이다. 확정/취소와 저장을 분리한다. 드래그 취소·되돌리기는 해당 영역의 좌표만 되돌려 다른 대사의 편집을 보존한다. 작업 조회 중지·재개와 실제 엔진 취소를 구분하고, 수동으로 옮긴 페이지·검수 탭을 처리 콜백이 다시 빼앗지 않는다.
- **DX:** `studio-state.ts`의 순수 전이 함수가 문서 이력, 단일 비동기 작업, 연결 검사, 페이지 처리를 관리한다. 시간·ID 생성은 reducer 밖에서 한다. 성공·실패·중지 콜백은 요청 ID와 원래 프로젝트/페이지에만 적용한다. 업로드·OCR 수신·처리 결과는 undo 경계다.
- **AX:** main의 `data-workspace-state`, `data-operation`, `data-save-state`, `data-project-id`, `data-page-id`, `data-page-state`, `data-mode`는 읽기 전용 관찰값이다. 페이지/텍스트 영역은 `data-page-id`/`data-block-id`로 식별한다. 버튼의 disabled/pressed/expanded/current, dialog의 busy와 저장 경고의 live region을 제공한다. 별도의 숨은 쓰기 API나 인증 우회 경로는 만들지 않는다.

### 저장 호환성과 충돌

기존 IndexedDB `trio-studio-v1`의 `workspace/current`와 v1 프로젝트 파일을 유지한다. 로컬 복원에서는 긴 대사와 기존 처리 기록, 직접 추가한 영역을 외부 입력 제한으로 잘라내지 않는다. 이전 버전의 복원 이미지가 있는 0영역 결과도 사용자가 원본을 보고 검수할 수 있다.

`storageRevision`은 기존 v1 레코드에 추가되는 선택 필드다. 값이 없는 기존 레코드는 0으로 읽는다. 읽기-비교-쓰기 전체를 하나의 IndexedDB readwrite 트랜잭션에서 수행한다. 다른 탭이 먼저 저장했거나 저장 버전이 바뀌면 덮어쓰지 않고 현재 창의 편집을 유지하며 프로젝트 백업을 안내한다. 자동 병합이나 강제 덮어쓰기는 제공하지 않는다. 충돌 상태의 프로젝트 백업은 TRIO로 열리며 빈 프로젝트도 지원한다.

### 검증 근거와 한계

- 기존 검사 12개를 유지하고 상태·경쟁·복원·긴 데이터·작업 재개·이력 경계 검사를 추가하여 패널 전이 검사 3개를 포함하여 총 44개를 검증했다.
- 브라우저에서 기존 v1 프로젝트 복원, 더블클릭 편집과 undo/redo, 확정 전 초안의 새로고침 복원, 범위 메뉴 Esc 닫기를 확인했다.
- 두 탭에서 실제 저장 충돌을 만들어 선행 탭의 내용이 보호되고 후행 탭이 백업 안내를 표시하는 것을 확인했다. 빈 프로젝트의 TRIO 백업 파일도 다운로드했다.
- 드래그 뒤 undo가 다른 대사 편집을 유지하는 경로를 확인했다. 포인터 취소의 데이터 보존은 순수 전이 검사로 확인한다.
- 실제 OCR/번역 서버가 제공되지 않아 실 엔진 네트워크 완주는 확인하지 않았다. 엔진 경계는 제어된 응답으로 생성/실패/중지/ID 재개를 검증한다.
- 생성 요청을 보낸 직후 브라우저 프로세스 자체가 종료되어 작업 ID 응답을 받지 못한 경우는 기존 엔진 API만으로 성공 여부를 확정할 수 없다. 새 업로드를 자동 재시도하지 않고 엔진 기록 확인을 안내한다.
- 브라우저 프로세스의 강제 종료 직전 아직 완료되지 않은 저장은 보장할 수 없다. 저장 완료 표시는 실제 최신 스냅샷 커밋 이후에만 제공한다. 다운로드는 요청 완료와 OS의 파일 저장 완료를 구분한다.


## 정렬·반응형 후속 검증
